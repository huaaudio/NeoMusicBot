# 发布测试版

`Make Release` 只发布 `v主版本.次版本.修订版本-alpha.N`、`-beta.N` 或 `-rc.N` 标签。
例如标签 `v0.5.0-beta.1` 必须对应 POM、JAR 和 SBOM 中的 `0.5.0-beta.1`。
当前开发版本不会自动变成测试版；修改版本号后必须重新运行完整 CI。

## 发布前

1. 完成 [审查记录](modernization-audit.md) 中的必要修复、依赖迁移和发行材料检查。
   特别注意独立媒体工具的许可证及对应源码；Maven 许可证检查不能代替整个发行包的检查。
   [发行材料记录](distribution-licenses.md) 中的未完成项必须解决；provider 清单仅证明材料与包相符。
2. 在默认分支提交最终代码、测试版版本号和文档，等待该提交的 `Build and Test` 完成。
   Windows/Linux 的编译、测试、原生语音自检、干净目录解压验证，以及锁定音源检查都必须通过。
   本地音源成功或部分 CI 绿色不能替代整次流水线成功。
   本仓库启用[隔离的一次性媒体 runner](isolated-media-ci.md) 后，默认分支的普通 push
   会直接把媒体任务交给运行中的本机控制器。电脑和控制器需要在线，工作区须与远程提交一致；
   排队不算通过。默认分支手动运行仍可使用自定义标签。媒体检查必须实际通过，不能用本地报告替换。
3. 准备发布说明，包含主要功能、与原项目的差异、迁移步骤、准确的测试范围和已知限制。
   本地 Opus/RTP 自检、在线短时解码、真实 Discord 语音验收需要分别说明；没有实际执行的项目标为未验证。
   已有[说明草稿](prerelease-notes.md)，发布前必须用最终提交和实测结果更新，删除草稿标记与维护者清单。
4. 从默认分支运行 `Make Release`，输入该次构建的 run ID、匹配的测试版标签和发布说明。
   构建之后如果默认分支已有新提交，需使用新提交对应的成功构建，不能混用旧产物。

## 自动校验与发布

- 来源必须是本仓库默认分支的 `push` 或 `workflow_dispatch`，工作流名称和路径必须匹配。
  构建与发布执行的完整提交 SHA 必须相同。
- 直接下载已测试的两个平台 ZIP，不重新打包。检查 ZIP 哈希、解压验证报告的提交与版本、
  JAR/POM/SBOM 版本、包内外 SBOM 一致性、平台标识和工具锁定信息。
  同一套平台检查也在每次构建中执行，以真实 CI 产物验证发布校验程序。
  `provider.native=passed` 要求 Canvas 来源记录和所有 native 文件符合仓库固定定义，
  并在解压后的离线环境完成像素绘制和 PNG 编码。
  `provider.native.materials=passed` 同时核对该平台实际安装库、原始声明及对应源码材料；
  Linux 使用不可变原生资产 r2，Windows 使用固定的官方配套库材料。
  `runtime.ytdlp.notices=passed` 核对实际 yt-dlp 程序、上游完整声明及明确补充原文，
  对应源码交付的审查仍须单独完成。
  `provider.quickjs=passed` 要求安装和缓存中的七个 WASM 均与固定 npm 原包匹配，
  对应 QuickJS/WASI/LLVM 源码、原始声明和实际编译器标识通过校验。
  `runtime.deno.materials=passed` 要求实际 Deno 程序哈希、固定源码、原始声明与补充材料
  在干净解压后逐项匹配；此门禁不替代内嵌组件适用声明范围的审查。
- 媒体报告必须属于同一提交、同一工具集，且三项锁定检查都通过。在线检查失败时不会创建标签。
- 原子创建新标签；已有标签或 Release 不会被覆盖。上传为 Pre-release 草稿后，下载全部资产，
  将文件集合与每个文件的 SHA-256 同已验证产物逐项比较。
- 校验通过后公开为 Pre-release，并明确不设为 Latest；随后再次检查标签提交、Release 状态和下载资产。
  [GitHub CLI 文档](https://cli.github.com/manual/gh_release_create)说明了草稿、测试版及 Latest 标记的行为。

发布资产包括两个完整 ZIP、各自的校验文件与 JSON/XML SBOM、两个解压验证报告、媒体报告、
带源提交和构建 run ID 的 `NeoMusicBot-build.json`，以及覆盖所有这些文件的 `SHA256SUMS`。

## 失败处理

校验失败会停止发布。标签创建后的失败可能留下标签及草稿，便于检查现场；重跑不会覆盖它们。
先核实失败阶段及远程实际状态，再决定保留、清理本次失败产物，或使用新的测试版版本重新构建。
如果公开后的读回检查失败，流水线仍会报错；不能把已存在的 Release 当作完整验收通过。

发布流程代码和自动化测试通过，只能证明这些检查已实现。首次真实上传、读回和公开操作
仍需在满足发布条件后执行，并记录对应运行结果。
